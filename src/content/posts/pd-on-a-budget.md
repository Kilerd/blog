过去一周多，我几乎都泡在一件事上：给我们的 TTS 推理服务做 PD 分离（Prefill/Decode Disaggregation）。

PD 分离不是什么新鲜玩意儿，DistServe、Mooncake、Dynamo、llm-d，社区里一抓一大把。可真正动手之后我才发现，这些方案都有一个默认前提：你得有 RDMA，最好还有跨机的 NVLink。而我们手里有的是一堆消费级的 RTX 5090，外加几台网卡压根没接线的 B300。

所以这篇讲的是一个「穷人版」的 PD：P 和 D 只在同一台机器里配对，KV 不出这台机器。路上踩的坑比我预想的多得多，有几个还挺灵异的。

## 为什么非做不可

先交代一下背景。TTS 是我们的主营业务，用户要的是流式音频：模型吐出一段 token，声码器就合成一段音频推给用户。我们的首段音频窗口是 `10,10,12,32,64`，也就是说第 10 个 token 出来，用户就能听到第一段声音，后面的窗口越来越大。

这就带来了一条硬底线：**每一路流的生成速度都不能低于 42 tok/s**，也就是 RTF ≤ 0.5，生成要比播放快一倍。一旦某一路掉到底线以下，播放缓冲被吃空，用户听到的就是一顿一顿的卡顿。

单体部署（同一张卡既做 prefill 又做 decode）的问题出在 prefill 上。TTS 的 prompt 里塞着参考音频的 token，用来克隆音色，中位数八百多行，p99 接近六千行。遇到一个没见过的音色，整段参考都要冷算一遍，在 5090 上大约每一千行 50 ms。这一次 forward 期间，卡上所有正在解码的流都得等着。

一句话：**一个冷请求进来，所有正在播放的流一起顿一下。**

我们在 5090 上用线上流量的配比（prompt 长度分布、20% 的冷参考、平均输出 126 个 token）做了一次对照测试，单体用 1 张卡，PD 用 1P1D 两张卡：

| 并发路数（整组） | 单体 卡顿流占比 | 单体 最慢 1% 流速 | PD 1P1D 卡顿流占比 | PD 最慢 1% 流速 |
|---|---|---|---|---|
| 8 | 0.12% | 48.1 tok/s | 0 | 56.3 tok/s |
| 16 | 0.32% | 38.1 tok/s | 0 | 50.1 tok/s |
| 24 | 5.33% | 33.6 tok/s | 0 | 45.1 tok/s |
| 32 | 19.28% | 27.5 tok/s | 0 | 42.7 tok/s |
| 40 | 54.02% | 25.7 tok/s | 0 | 38.5 tok/s |

单体从 8 路开始就有流卡顿，PD 一直到 40 路都是 0。PD 用了两张卡，所以公平的比法是看每卡路数：同样每卡 16 路，单体有 0.32% 的流会卡，最慢 1% 只有 38 tok/s；PD 跑 32 路，0 卡顿，最慢 1% 还有 42.7 tok/s。

更扎心的是，线上的单体当时每卡跑着 22 路左右。按这张表算，意味着有 0.7% 到 5% 的流在卡。

「主营业务就是 TTS，这个不做不行啊。」于是就有了这一周。

## 第一堵墙：别人的 PD，我们的硬件跑不起

一开始我是这么想的：PD 嘛，抄就完事了。SGLang 自带 PD，KV 用 Mooncake 传，P 和 D 各一组机器，中间走 RDMA，完美。

然后我去看了一眼我们的机器。

- **5090 集群**：消费级显卡，没有 NVLink。GPUDirect RDMA 也没有：驱动里没有 `nvidia_peermem`，dma-buf 导出直接报 `NOT_SUPPORTED`，所以想走 RDMA 只能先拷回主机内存。机器之间是 25 GbE。
- **B300 机器**：机内有 NVLink，每台还配了 8 张 ConnectX-8 网卡，就挨着 GPU。但是，**没接线**，端口状态 `DOWN`。机器上能用的 IB 口是 NVLink 自己的管理网，100G 的 RoCE 网卡又没暴露给 Pod。跨机只剩 Pod 网络，实测上限 3.4 GB/s 左右。

一个 2k token 的 prompt，KV 是 144 KiB/token × 2048 ≈ 288 MiB。我们实测了一下搬这么一份 KV 要多久：

![硬件约束：同机与跨机](/statics/images/pd-on-a-budget-hardware.svg)

同机：B300 走 NVLink 0.54 ms，5090 走 PCIe P2P 5.6 ms。跨机：B300 85 ms，5090 104 ms，分别慢了 160 倍和 19 倍。5090 跨机用 TCP 还是 RoCE 都一样，25 GbE 的线速摆在那里。

那么问题来了：decode 一步也就十几毫秒，第一段音频要等 9 步左右。每个请求先花 100 ms 搬 KV，那还拆个什么劲？

后来做社区调研的时候，我还看到 NVIDIA 自己的 PD 决策流程图，要求有 RDMA、输入输出长度比大于 8:1；他们的旧版指南里，1k token 的输入 PD 几乎没有收益。我们 1–2k token 的 prompt，正好落在文献说 PD 最不划算的角落。我们做 PD 唯一的理由，是每路流速有硬底线，需要把 decode 和 prefill 隔开。

结论很朴素：**P 和 D 必须在同一台机器上配对，KV 不出这台机器。** 跨机只当降级兜底，不当扩容手段。

## 第二堵墙：同一台机器，容器之间互相看不见

好，那就同机。同机总简单了吧？

并没有。K8s 的 device plugin 只给每个 Pod 挂它自己申请的那张卡，而 CUDA IPC 要求导出显存的那张卡在导入方的容器里也看得见。我在 B300 上挨个试了一遍：

- 传统的 `cudaIpcOpenMemHandle`，两个 Pod 之间：`invalid argument`。同一个 Pod 里两个容器、开了进程命名空间共享：还是一样。
- 用 unix socket 传 cuMem 的 POSIX fd：`CUDA_ERROR_INVALID_DEVICE`。
- 用 FABRIC 句柄：没有 IMEX 通道时直接 `NOT_PERMITTED`；手动建了通道，跨容器导入又变成 `NOT_SUPPORTED`，因为宿主机那个版本的驱动压根没带 `nvidia-imex`。

一圈下来全军覆没。这时候我想起了上一篇[《GPU 小偷》](/thief-of-gpu)里的罪魁祸首：`NVIDIA_VISIBLE_DEVICES=all`。一个不申请 GPU、但设了这个环境变量的容器，能看见整台机器所有的卡。上次它是事故元凶，这次它成了救命稻草。

我先写了个原型：一个这样的「搬运工」容器，替 P 和 D 打开双方的 IPC 句柄，在 B300 上 281 MiB 拷贝 0.37 ms，744 GiB/s。路是通的。

后面两种卡走了两条不同的路。

### B300：让 P 直接写 D 的显存

后来 B300 的驱动升级了，宿主机上的 IMEX 也跑起来了，FABRIC 句柄跨 Pod 导入终于能用，而且不需要特权，Pod 只申请一张卡就行。于是方案变成：D 用 FABRIC 内存分配自己的 KV 池并导出句柄，P 导入之后，用一个 gather kernel 把散落的源行直接写进 D 的页里。

效果：2000 条散落的行（281 MiB）0.47 ms。作为对比，上游 Mooncake 的 NVLink 路径是逐块拷贝，同样 2048 条散落的行在我们 Pod 里测出来要 296 ms。端到端跑了两万一千多次传输，全部走 fabric，KV 校验 0 失配。64 路并发下 TTFT p50/p95 是 54/140 ms，同样的负载走 TCP 是 12.8 s/19.1 s，基本已经崩了。

### 5090：一个看得见所有卡的代理

5090 没有 FABRIC，就只能靠那个搬运工了。我们在 Mooncake 上 fork 了一个 [`nvlink_proxy`](https://github.com/Kilerd/Mooncake)：一个不申请 GPU、但看得见所有卡的守护进程，P 和 D 通过 unix socket 把自己的显存登记给它，它打开双方的 CUDA IPC 句柄，在目标卡的上下文里做 P2P 拷贝。5090 上第一次测，286 MiB 6.0 ms，47.6 GiB/s。

听起来很顺？第一个坑马上就来了：大部分 5090 节点上的 GPU 都设成了 `Exclusive_Process` 模式，P/D 占了卡之后，守护进程根本建不了上下文。只能先挑 compute mode 是 Default 的那几台跑起来。

第二个坑是碎片。金丝雀接上真实流量后，KV 传输平均 21 ms，跑着跑着涨到了 44.75 ms。一看，每个请求要拷大约 7,660 个只有几 KB 的小块，因为 KV 池是按 token 分页的，一个请求的 KV 散得到处都是。我们先在守护进程里加了 gather kernel 处理小块，单批从 11.71 ms 降到 3.86 ms；又把 gather 挪到源卡那一侧，kernel 再快 2.4 倍。

结果还是越跑越慢。复现了一下才发现是池子本身碎了：刚重启的池子，一次冷传输只有 72 个块，3.84 ms；跑了一阵子之后变成 105,660 个块，48.5 ms。「合并传输吧，不然全是碎片操作。」我当时是这么拍板的：P 先把要发的行 gather 到一块连续的 staging 区，一次传过去，D 再 scatter 回自己的页。同样碎掉的池子，传输回到 3.79 ms、72 个块，TTFT p50 从 142 ms 降到 100 ms。

再后来，这个守护进程从每个节点一个的 DaemonSet，挪进了每个 PD 单元自己的 sidecar：跟着单元一起滚动升级，客户端和守护进程的版本不会再错开，崩了也只影响自己这一个单元。

## 最灵异的部分：数据悄悄消失了

PD 单元第一次正式往 5090 上铺的时候，有几个单元的 decode 在第一个请求上就挂了：采样 kernel 里 `device-side assert triggered`。

打开 KV 校验，再给 D 加上 `CUDA_LAUNCH_BLOCKING=1`，真相大白了一半：D 这边 checksum MISMATCH。数据到 D 手里的时候就已经坏了，坏的 KV 算出坏的 logits，采样直接断言。

那数据是怎么坏的？接下来是我们的三连猜：

1. **「是 GPU0 的锅。」** 坏掉的单元都有一张卡在 PCI `01:00`，守护进程的默认上下文也恰好在 GPU0 上。听起来很合理，我们甚至准备好了临时方案：不让守护进程碰 GPU0。
2. **「是那个 PCIe 根复合体的位置。」** 读了一遍 sysfs，发现别的卡也各占一个根复合体，于是改口说特殊的是 `pci0000:00` 这个位置。
3. 最后有人干脆绕开所有 PD 代码，直接拿 torch 的 `dst.copy_(src)` 在卡对之间测。结论把前两个猜想都推翻了：**有两台机器，测到的每一对卡（带不带 GPU0 都一样）160 次拷贝 160 次全坏；第三台一次都没坏。** GPU0 纯属巧合，之前那个一直没出事的金丝雀，恰好跑在好的那台机器上。

坏的方式也很有意思：目标显存保持着拷贝前的填充值，一个字节都没被写进去，而 CUDA 没有任何报错。`cudaDeviceCanAccessPeer` 说可以，`nvidia-smi topo -p2p` 也说 OK。P2P 拷贝「成功」了，只是数据没了。

这种 bug 最可怕的地方在于它安静。我们最后上了三层防线：

- **端到端 KV 校验**：P 发送前对源行求和，D 落地后对自己的页再算一遍，对不上就直接中止这个请求、把错误告诉客户端，绝不拿坏 KV 去解码。
- **每对卡的 P2P 自检**：守护进程在一个带看门狗的子进程里，先往目标显存写入哨兵值，再拷贝、逐字节比对，拷贝引擎和 gather kernel 两条路径都测。不过关的卡对直接拒绝 P2P。
- **主机内存中转**：被拒的卡对改走 GPU → pinned 主机内存 → GPU。

本来以为中转只是「慢但是对」，结果实测在坏机器上搬 2048 行，主机中转 5.98 ms，而好机器上直连 P2P 是 5.58 ms，两者都在 50 GB/s 上下，TCP 兜底则要 90 ms。中转只比 P2P 慢 0.4 ms，却比 TCP 快十几倍，这算是整件事里唯一的惊喜。

后来 SRE 把这几台机器修好了，再扫一遍，所有卡对都比特一致。有一种说法是消费卡的 P2P 疑似依赖社区打过补丁的驱动分支，这点我们没有确认，反正自检和校验一直开着。

同一时期还有一个「跨插槽迷信」。早期金丝雀上测到，跨 CPU 插槽的 P→D 拷贝（1k–2k 行）p99 109 ms，同插槽只有 17.5 ms。我当时就想上 kubelet 的拓扑管理器，把 P 和 D 钉在同一个插槽。后来换成每个单元自带 sidecar，在线上对比了 30 分钟：跨插槽 p99 18.8 ms，同插槽 19.1 ms，那个差距再也没出现过。怀疑是当时共享的 DaemonSet 和旧版守护进程造成的，但没再去验证。差点为一个不存在的问题去改集群配置。

## 先测量，再动手：PD 的时间都去哪了

PD 跑通之后，下一个问题是：为什么它比单体还慢？B300 上接真实流量时，稳态下 PD 的 TTFA p50 比单体高 40 ms。

一开始我也想拍脑袋：是不是传输慢？是不是 LB 多了一跳？后来我给自己定了个规矩：「先在代码里加分阶段的计时日志，跑一遍看时间花在哪，再针对性地修。」不许猜着优化。

具体做法是给 LB、P、D 三个进程在每个请求的关键节点都打上时间戳，再把线上流量（7.8 万个请求，按线上的到达时间、prompt 长度和缓存命中长度合成）回放到一个隔离的测试组里。所有 Pod 在同一台机器上、同一个时钟，各段首尾相接，加起来正好等于客户端实测的时间。

![最慢 1% 请求的时间瀑布](/statics/images/pd-on-a-budget-waterfall.svg)

照着这张瀑布图往下挖，结果和我的直觉差得挺远：

**第一名是 Prefill 的调度准入，不是传输。** P 的调度循环在 GPU forward 期间不收新请求，收的时候又是一个一个串行地反序列化。TTS 的 prompt 是一个「一千多个、每个 11 个 int 的 list」，反序列化慢，还制造了大量短命对象，突发时 GC 每秒吃掉 77 ms，P 的调度进程直接打满一个核。修法是让 HTTP 进程在 C 里校验 prompt，打包成一个 int64 数组传给调度器。光这一项，突发时 P 准入的 p99 就从 667 ms 降到 149 ms，首 token p99 从 904 ms 降到 256 ms；再加上「forward 期间也收请求」，突发时 P 收请求的 p99 又从 119 ms 压到 43 ms。D 那边同理，打包之后 D 收请求的 p99 从 36 ms 降到 0.2 ms，最慢 1% 的流速从 29.7 翻到 58.2 tok/s。

**Decode 的步子被主机拖住了。** 我们移植的 PD 循环里，decode 只有非 overlap 的版本，GPU 算完一步要等主机处理完才开始下一步。把 overlap 调度移植到 D 上之后，同样负载下步时从 12.6 ms 降到 9.0 ms，GPU 忙碌率从 79% 到 98%。为了确认 overlap 不改变输出，我们跑了两组各十万条流的自然结束对照，输出长度和结束原因在统计上分不出差别，0 错误。

**输出路径。** D 的 HTTP 进程用 uvloop，而 uvloop 的 `write` 要等这一轮事件循环跑完才真正刷出去。调度器每一步发一个批次过来，N 路流在同一轮里被唤醒，于是每一路都得等最后一路处理完，每个事件 30–47 µs，延迟大约是 N 乘以这个数。修法是让还在首窗（前 10 个 token）里的流先写，顺便把每个事件瘦身、一次多取几条调度消息。D 上有 200–300 路时，第 10 个 token 的转发 p90 从 11.2 ms 降到 5.2 ms，SSE 字节一个没变。

**还有 GC，这个我是真没想到。** B300 上拆 decode 的主机时间，排第一的居然是 Python GC：384 路时每步吃 8.3 ms。D 的 HTTP 进程一次完整回收要 563 ms。更离谱的是，**二代回收每次回收掉的对象数，中位数是 0**，纯粹是在一遍遍地遍历在途请求的 prompt 和 radix 树的 key。把解析完的 prompt 及时丢掉、把 radix key 和 prompt 行换成 GC 不追踪的 tuple 之后，256 路时 TTFT p95 从 585 ms 降到 111 ms。

最后剩下的是物理：2k 上下文时，每多一路，一步大约多 54 µs，其中 42 µs 是 attention 在读这一路自己的 KV（每路约 295 MB），读带宽已经到了 HBM 标称的 88%。这一块没什么好修的。

也有不少我们**决定不做**的事：

- 换 attention kernel、融合小 kernel：风险大，收益不确定。
- FP8：冷 prefill 能快 1.5–1.8 倍，但要重新做音质评估，而且 P 用 FP8、D 用 bf16 会让我们逐位比对的正确性关卡失效。最后拍板不做。
- 同音色前缀只读一次：KV 字节能少三到五成，但步时只省 0–5 ms，因为容量的瓶颈在主机不在 attention。
- 逐层传输：尾延迟只能省 12 ms 左右，要花一周。
- 跨机的 L3 KV 缓存：第一道关卡就没过（Mooncake 的 TCP 单线程只有 2.9 GB/s），后来虽然做出来了，也只能省 12–15% 的 prefill 计算，现在默认关着，先放一放。

## 部署形态：越简单越好

P 和 D 怎么配比，我们也绕了一圈。按理说 TTS 是 decode 重、prefill 轻：1P1D 跑到 40 路时，P 的 GPU 只有 31% 在忙。在 5090 上，1P2D 能做到每卡 24 路，是测过的形态里密度最高的；2P1D 只能把首包时间压一点点。B300 上我们也拿真实流量从 1P1D 扩到过 1P2D。

但多 P 多 D 意味着 LB 里要有路由：音色亲和、挑同机的 D、每个 Pod 单独的 DNS，故障域也跟着复杂起来。最后我选了最笨的办法：「浪费一点资源，换部署简单。」

![部署架构](/statics/images/pd-on-a-budget-architecture.svg)

- **固定 1P1D 单元**：一个 Pod 里放 LB、P、D 和两个 sidecar，P 和 D 永远在同一台机器上。P 有七成时间闲着，我们认了。
- **Router 只管分发到单元**，按会话亲和，不关心单元里面是什么。LB 也只负责转发给本单元的 P 和 D，多 P 多 D 的路由逻辑全删了，Python 版的 LB 从 1651 行瘦到 1324 行。
- **KEDA 按 decode 的在途路数扩缩单元个数**，目标值留出突发余量。

LB 后来又用 Rust（tokio + hyper）重写了一遍。原因很简单：Python 版是单个 asyncio 循环转发所有 SSE 事件，在 CPU 压测里，600 路时它自己引入的 p99 延迟就有 33.9 ms，Rust 版只有 0.81 ms，CPU 占用也只有原来的四成左右。行为上和 Python 版做了逐字节对齐，61 个用例（包括各种故障注入）结果一致。顺手还修掉一个问题：uvicorn 收到 SIGTERM 会直接切断还在播放的流，Rust 版会先停止接新请求，把在途的流放完再退出。

## 上线之后才学到的事

### 新单元的前几个请求要等 5 秒

刚就绪的单元，头几个请求的 TTFT 是 5–6 秒。查下来，九成时间是 D 卡在第一个 decode 步上 5.2–5.7 秒，期间正好只有一个 CPU 核在忙：CUDA graph 之外的那些 Triton kernel 在第一次用的时候 JIT 编译。

单体有 SGLang 自带的启动预热，PD 却没有走过真实的 P→D 路径。我们没去搞持久化的编译缓存，而是让 pd-lb 在报告就绪之前，自己发几个合成请求把真实的 P→D 链路走一遍：第一轮一个 1247 行的请求，第二轮四个不同长度的并发请求，全部完成且最后一轮每个事件间隔都小于 1 秒才算预热通过。就绪时间多了 6–8 秒，首轮请求的 p95 从 5.6–6.2 秒降到 330 ms。

### 启动 148 秒到 47 秒

上线之后还发现，PD 单元启动要两分多钟，单体只要一分钟出头。一测，全是浪费：

![PD 单元启动时间](/statics/images/pd-on-a-budget-startup.svg)

D 从来不跑 extend，却捕获了 58 个尺寸的 piecewise graph；P 从来不 decode，却捕获了 bs 1–128 的 decode graph；七八个 JIT 模块在第一次使用时串行 nvcc 编译，每个 5–9 秒，D 的关键路径上加起来约 49 秒；HiCache 的主机内存池还是同步锁页的，D 的 64 GiB 要 20.5 秒。

改法都很直白：按角色只捕获自己用得到的 graph，启动时并行预编译 JIT，P 的 piecewise 梯子封顶到 2048 token（再往上跑 eager，只慢 0.25%–1.9%），主机内存池改到后台锁页。148 秒 → 79 秒 → 47 秒。

然后又来一个坑：某个单元的后台锁页花了 508.7 秒。那台机器空闲内存只剩 6 GiB，透明大页（THP）在内核里拼命回收和整理内存，内存 PSI 的 full 指标到了 44%–74%。最后加了个兜底：预分配一旦慢到每 GiB 超过 1 秒，剩下的部分就退回 4 KiB 的普通页。

### 传输失败之后，KV 页什么时候能还？

这是整个项目里我觉得最难的一个问题。

P→D 的传输失败了（P 卡住、守护进程重启、网络抖动），D 为这个请求预留的那些 KV 页，什么时候可以拿去给别的请求用？如果 P 其实还活着，它的写入还在路上（TCP 接收端还在应用已经收到的数据，守护进程还在拷贝），D 却已经把页给了下一个请求，那这次迟到的写入就会悄悄改掉别人的 KV。没有报错，只有一段听起来不对的音频。

这个设计前后改了三版，前两版都被独立 review 打穿了：

1. **第一版**：写入截止时间一过，或者判定 P「失联」（两次健康检查失败），就释放。review 指出：「失联」只是两次检查没通过，而且永远不会被撤销，一个活着的 P 完全可能迟到写入，污染别人的 KV。另外按时间释放的上界也不成立，TCP 的进度计时器会一直往后滑。
2. **第二版**：只认证明：P 回了 ABORT_ACK，或者 P 的实例 ID 变了（说明重启过）。为此我们给 Mooncake 加了「这批传输已经静止」的接口。结果这个接口的 review 又发现：对于老协议的对端，被切断的写入已经报告「静止」，之后居然还能落下 2 MiB 多的数据，而且复现出来了。
3. **第三版**：Mooncake 的批次静止接口加上 TCP 协议 v3，请求带 ID 和剩余时间，接收端丢弃迟到的数据块并确认终态。P 只在能证明静止时才回 ACK，否则一直扣着。兜底也有：P 扣着的 ACK 攒到 3 个就自己退出，重启后的新实例本身就是证明；D 被扣住的容量超过 25% 就自己摘流排空。客户端则在发现失败的第一时间就收到错误，不用陪着等。

最后在一个 5090 单元上做了 GPU 故障注入：暂停 P、杀掉 P、暂停守护进程、暂停 D 的输出。第一轮还抓到两个恢复相关的 bug，修完重跑全部通过，一万三千多次 KV 校验 0 失配。

### 容量测试

还是开头那次 5090 对照测试，换成图来看：

![卡顿占比与最慢 1% 流速](/statics/images/pd-on-a-budget-stutter.svg)

TTFA 这里要说句实话：在 5090 上，单体和 PD 都达不到我们定的首段音频目标（E2E p95 150 ms / p99 200 ms），哪怕只有 2–8 路，地板也在 p95 280–300 ms、p99 350–410 ms。一个长参考的冷 prefill 每千行 50 ms，首段音频前还有 9 步每步至少 15 ms 的解码，这是 5090 的物理。PD 改变的是卡顿，不是首包。

之后 5090 集群上金丝雀所在的那条产品线，流量全部切到了 PD 单元，由 KEDA 扩缩。最后一版（故障路径加固 + Mooncake 新版本）上线前后各看了 30 分钟：网关口径的 TTFT p50 基本不变（277 → 275 ms），p99 从 779 ms 降到 638 ms；单元重启 0 次，KEDA 缩容两次都是正常排空；KV 校验 138,395 次，0 失配。30 分钟的窗口不算长，p99 的改善里可能也有负载变化的成分。

正确性上，我们一直跑着一个金丝雀：同样的文本分别走 PD 和单体合成，再用 ASR 转写算字错率（CER）。<!-- TODO 核对：CER 金丝雀是否为同文本成对比较 -->同语种累计 26,259 对，PD 减单体的 CER 差是 +0.023 个百分点，95% 置信区间 [−0.027, +0.073]，在 ±0.5 个百分点的等价区间内，各个长度、语种、音色的子组也都等价。

### 诚实的代价

PD 不是免费的午餐：

- **低并发时它不省卡。** 1P1D 用两张卡干单体一张卡的活，P 七成时间闲着。
- **它省的是「不卡顿」这个前提下的卡。** 按「0 卡顿、每路 ≥ 42 tok/s」这条线，单体每卡大约只能跑 8 路，而且 8 路时已经有 0.12% 的流在卡；PD 大约是每卡 16 路。
- **它不让首包更快。** 按每卡算，同样 16 路，PD 的 TTFA p95 还比单体略高（392 vs 347 ms）。
- 如果你能接受线上那 0.7%–5% 的卡顿，单体每卡 22 路反而是最省卡的。只是我们的业务接受不了。

## 碎碎念

**先测量，直觉一次又一次地错。** 跨插槽、GPU0、GC 都是。还有一次，最后一版上线后，CER 金丝雀里长句子组 PD 略差，符号检验 p≈0.004，吓了我一跳。挨个排查了截断、HiCache 回载、前缀命中、负载，全都对不上；再等一等样本，偏差自己回归了（1,732 对，+0.016 个百分点，置信区间包含 0）。小样本的显著性，看看就好。

**消费级硬件能用，前提是按「它会静默出错」来设计。** 校验、自检、兜底，一个都不能少。真正可怕的从来不是报错，而是不报错。

**拓扑越简单越好。** 1P1D 浪费了 P 的算力，但换来的是：没有跨单元的路由、没有跨机的 KV、扩缩就是加减单元。出了问题，我能在脑子里把整条链路过一遍。

**PD 不是万能的。** 我们另一个模型 S1，在 PD 上不改一行代码就能跑起来，冒烟测试 0 错误，但我们最后没上。它每张卡只有 2–6 路并发，服务端 TTFT p99 不到 115 ms，每路流速 89 tok/s。PD 的收益来自「decode 卡上有三十多路流，被长 prefill 打断」这种场景，S1 根本没有这个问题，一个单元还要多占一张卡。

还有一条血泪教训就不展开了：测试用的 Pod，权限给到刚好够用为止。
